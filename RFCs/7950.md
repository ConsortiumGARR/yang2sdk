### 📄 RFC 7950: YANG 1.1 Data Modeling Language

#### 1. Metadata & Standards Track
* **ID**: RFC 7950 (Obsoletes RFC 6020) | August 2016.
* **Author/Editor**: M. Bjorklund (Tail-f Systems).
* **Category**: Standards Track.
* **Scope**: Defines syntax & semantics of YANG 1.1, mapping rules to NETCONF.

---

#### 2. Key Architectural Concepts & Conformance

##### 2.1 Definitions, Scoping & Lifecycle
* **Scoped Definitions**: `typedef` / `grouping` nested within a parent node MUST NOT shadow definitions at a higher scope in the same hierarchy (no identifier collisions).
* **Datastore Modifications**: Server-side modifications (e.g., auto-populating default values without explicit client configuration) are permitted but formal out-of-band signaling rules are out-of-scope.
* **Coexistence (v1 $\leftrightarrow$ v1.1)**:
  * $YANG_{1.1}$ $\neq$ include $YANG_{1.0}$ submodules.
  * $YANG_{1.0}$ $\neq$ include $YANG_{1.1}$ submodules.
  * $YANG_{1.0}$ $\neq$ import $YANG_{1.1}$ by revision.
  * $YANG_{1.1}$ $\implies$ import $YANG_{1.0}$ by revision.

##### 2.2 Conformance Mechanisms (Section 5.6)
1. **Basic Behavior**: Strict syntax/semantics contract between client & server.
2. **Features**: Conditional compilation/support of model components using the `feature` and `if-feature` statements.
3. **Deviations**: Declares server-side limitations/deviations from the module contract using the `deviation` statement.

##### 2.3 NETCONF Capability Announcement
* A server MUST implement `"ietf-yang-library"` (RFC 7895), listing all implemented modules in `/modules-state/module`.
* **Capability URN**: `urn:ietf:params:netconf:capability:yang-library:1.0?revision=<date>&module-set-id=<id>`

##### 2.4 Multi-module Dependency Resolution
If Module $A$ imports Module $B$, or references $B$ in `augment` / `path`:
* If server supports these nodes, the server MUST implement a matching revision of $B$.
* If $A$ imports $C$ without a revision date and the server does not implement $C$ (e.g., $C$ only provides type declarations), $C$ MUST be listed in `/modules-state/module` with `conformance-type` set to `"import"`.
* If multiple modules import $C$ without specifying a revision date, the server MUST use the most recent revision of $C$ listed.

#### 3. Lexical rules & Identifiers

##### 3.1 Tokenization & Whitespace Rules
* **Format**: UTF-8 files. Line endings: CR+LF or LF.
* **Comments**: C++ style (`//` or `/* ... */`). Ignored inside quoted strings.
* **Strings**:
  * *Unquoted*: Separated by WSP, tab, LF/CR, `;`, `{`, `}`, `"`, `'`, comments. Backslash `\` is a literal.
  * *Double-quoted*: Backslash escapes (`\n`, `\t`, `"`, `\\`). Strips leading whitespace up to the column of the starting quote. Strips trailing whitespace before processing escape sequences.
  * *Single-quoted*: Preserves all literal characters. No single quotes allowed inside, even if escaped with a backslash.
  * *Concatenation*: Evaluated via the `+` operator after whitespace stripping but before resolving escape sequences.
* **Identifiers**: Match `[a-zA-Z_][a-zA-Z0-9\-_.]*`. Case-sensitive. Max length $\ge$ 64 characters.

##### 3.2 Global & Scoped Namespaces
* **Global**: Modules, Submodules, Extensions, Features, Identities.
* **Scoped**:
  * Typedefs, Groupings (scoped to descendants of the defining ancestor).
  * Data nodes (leafs, containers, lists, choices, rpcs, actions, notifications, anydata, anyxml) $\rightarrow$ unique within their parent schema node (or parent choice/case boundary).

---

#### 4. XPath Evaluation Context & Operations

##### 4.1 Evaluation Engine Characteristics
* **Version**: XPath 1.0. No strict document order.
* **Numerical Bounds**: XPath numbers are IEEE 754 double-precision floats. Explicit 64-bit integers (`int64`, `uint64`, `decimal64`) may lose precision during comparison.

##### 4.2 Namespace Resolution
* Unprefixed names in XPath expressions resolve to the namespace of the current context node.
* Prefixed names resolve according to the `import` and `prefix` statements in the defining module.

##### 4.3 Accessible Trees by Definition Context
| XPath Context Location | Accessible Data Tree Scope |
| :--- | :--- |
| **Config Node** | All configuration nodes in all modules. |
| **State Node** | All state nodes + running config datastore in all modules. |
| **Notification** | Notification instance payload + all state + running config. |
| **RPC/Action Input** | Operation instance payload + input parameters + all state + running config. |
| **RPC/Action Output**| Operation instance payload + output parameters + all state + running config. |

#### 5. YANG Statements Reference

##### 5.1 Basic Module Structure
```yang
module <module-name> {
  yang-version "1.1";
  namespace "<uri>";
  prefix "<prefix>";

  import <mod-name> { prefix <pref>; [revision-date <date>;] }
  include <submod-name> { [revision-date <date>;] }

  organization "<text>"; contact "<text>";
  description "<text>"; reference "<text>";
  revision <date> { description "<text>"; }

  // body-stmts...
}
```

##### 5.2 Submodules (`submodule`)
* Declared with `belongs-to <parent-module> { prefix <pref>; }`.
* Submodule prefix MUST match parent module prefix. Parent includes submodule via `include`.

##### 5.3 Typedef & Type Declarations
* `typedef <name>` defines a derived type from a base type. Cannot shadow existing types.
* Supports `default` and `units`. Base default is inherited unless explicitly overridden.

##### 5.4 Structs & Data Nodes

###### `container`
* **Non-presence**: Exists only for nesting. Semantically empty if no child nodes exist.
* **Presence**: Explicit semantic meaning. Created/deleted explicitly. Has `presence "<description>";`.
* Supports `must` constraints with optional `error-message` and `error-app-tag`.

###### `leaf`
* Represents a scalar value. Supports `type`, `default`, `mandatory true|false`, `units`, `must`.
* If `mandatory true`, the node MUST exist if its closest non-presence ancestor exists.

###### `leaf-list`
* Represents an array of scalar values. Supports `ordered-by system|user`.
* `min-elements` and `max-elements` enforce size constraints.
* User-ordered leaf-lists support the attributes `yang:insert="first|last|before|after"` and `yang:value="..."` in NETCONF payloads.

###### `list`
* Defines a sequence of records. Uniquely identified by keys (`key "<space-separated-leaf-names>"`).
* All key leafs MUST represent configuration if the list represents configuration.
* Keys cannot have default values or be marked optional.
* Supports `unique` statements to enforce uniqueness across multiple non-key leafs.
* User-ordered lists support the attributes `yang:insert="..."` and `yang:key="..."`.

###### `choice` & `case`
* Defines a set of mutually exclusive branches.
* If a case node contains a single data node, the enclosing `case` statement can be omitted (shorthand notation).
* Setting a leaf inside case $B$ implicitly deletes all active leafs from case $A$.
* Supports `default <case-name>` (must not have mandatory children).

###### `anydata` vs `anyxml`
* **`anydata`**: Represents unknown content that can be modeled using YANG. **(Recommended)**.
* **`anyxml`**: Represents an arbitrary, unmodeled raw XML chunk.
* Both are treated as opaque, indivisible units by NETCONF operations.

###### `grouping` & `uses`
* **`grouping`**: Reusable block of nodes. Does not instantiate nodes in the schema tree.
* **`uses`**: Instantiates a grouping.
  * Resolves namespaces at the target instantiation site.
  * Supports `refine` (overriding default, mandatory, config, units, must, min/max-elements).
  * Supports `augment` to add nodes locally inside the instantiated tree.

###### Operations (`rpc` & `action`)
* **`rpc`**: Top-level protocol operation.
* **`action`**: Bound to an instantiated data node (container or list with key). Cannot be defined at the top-level of a module, inside cases, or within other operations/notifications.
* Both define `input` and `output` parent nodes.

###### `notification`
* Represents an asynchronous event. Can be defined at the top level or bound to a data node.

###### `augment`
* Appends nodes to an external/local target node. Target MUST be container, list, choice, case, input, output, or notification.
* If augmenting mandatory config nodes into another module, the augmentation MUST be conditional (`when`).

###### `identity`
* Defines an abstract, untyped identifier for extensible type taxonomies.
* Supports multiple base inheritance (`base <identity-name>;`).

#### 6. Built-In Types

| Type | Description / Constraints | Lexical / Canonical Form |
| :--- | :--- | :--- |
| **`int8/16/32/64`** | Signed integers. Range constraint. | Decimal, Hex (`0x`), Octal (`0`). Canonical: Decimal, no leading `+` or zeros. |
| **`uint8/16/32/64`**| Unsigned integers. Range constraint. | Decimal, Hex (`0x`), Octal (`0`). Canonical: Decimal, no leading `+` or zeros. |
| **`decimal64`** | Fixed-point decimal. `fraction-digits` (1..18). | Optional sign + decimal point. Canonical: No `+`, contains `.`, $\ge$ 1 digit before and after `.`. |
| **`string`** | Unicode character string. `length`, `pattern`, `modifier invert-match`. | Raw XML characters. Canonical is identical. |
| **`boolean`** | True/False. | `true` or `false` (lowercase). |
| **`enumeration`** | Assigned-name set. Supports `value` and conditional `if-feature`. | Literal assigned name. Canonical is identical. |
| **`bits`** | Set of bit flags. Supports `position` and `if-feature`. | Space-separated list of active bit names. Canonical: ordered by bit position. |
| **`binary`** | Raw octet sequence. `length` constraint (number of bytes). | Base64 encoded string. Canonical: RFC 4648 format. |
| **`leafref`** | Dynamic reference to leaf/leaf-list. `path` (XPath subset), `require-instance`. | Formatted like the referenced type. Canonical is identical to target's canonical form. |
| **`identityref`** | Reference to an identity. `base` (1..n). | Qualified name (`prefix:name`). No canonical form due to XML namespace context dependency. |
| **`empty`** | Presence-only marker. No value. | Self-closing XML element (`<elem/>`). |
| **`union`** | Union of member types. Checked in order of definition. | Lexical form of matching member type. Canonical form of matching member type. |
| **`instance-identifier`**| XPath pointer to an instance node. `require-instance`. | Prefix-qualified path. No canonical form. |

#### 7. XPath Functions

* **`node-set current()`**: Returns the initial context node.
* **`boolean re-match(string subject, string pattern)`**: Evaluates standard XML Schema regex.
* **`node-set deref(node-set nodes)`**:
  * Resolves `leafref` $\rightarrow$ returns target nodes with matching values.
  * Resolves `instance-identifier` $\rightarrow$ returns the target node instance (if it exists).
* **`boolean derived-from(node-set nodes, string identity)`**: Returns true if any node in the set is an `identityref` derived from the target identity.
* **`boolean derived-from-or-self(node-set nodes, string identity)`**: Returns true if any node is an `identityref` equal to or derived from the target identity.
* **`number enum-value(node-set nodes)`**: Returns the integer value of the first node if its type is `enumeration`; otherwise returns `NaN`.
* **`boolean bit-is-set(node-set nodes, string bit-name)`**: Returns true if the named bit is set in the first node of type `bits`.

#### 8. Modifying and Updating Modules

##### 8.1 Backward-Compatible Changes
* Adding new `enum` or `bit` definitions (provided older values/positions remain unchanged).
* Expanding range, length, or pattern constraints.
* Adding a `default` statement to a leaf that previously had none.
* Removing or relaxing `must`, `when`, `mandatory`, `min-elements` restrictions.
* Adding new conditional nodes (using `if-feature`) or non-mandatory nodes.
* Changing a state data node (`config false`) to a configuration node (`config true`).

##### 8.2 Non-Compatible Changes (Require a New Module Name/Namespace)
* Deleting nodes or modifying existing semantic definitions.
* Tightening existing constraints (e.g., reducing ranges or lowering `max-elements`).
* Changing a configuration node (`config true`) to state data (`config false`).
* Adding mandatory nodes unconditionally.

---

#### 9. YIN: XML-based Syntax Mapping
* Elements belong to the namespace `"urn:ietf:params:xml:ns:yang:yin:1"`.
* Arguments are mapped either to XML attributes or child elements depending on the `yin-element` property.

#### 10. Standard NETCONF Error Map

| Violation | `error-tag` | `error-app-tag` | `error-info` / Target |
| :--- | :--- | :--- | :--- |
| **`unique` constraint** | `operation-failed` | `data-not-unique` | `<non-unique>` path |
| **`max-elements`** | `operation-failed` | `too-many-elements` | Identifies parent list |
| **`min-elements`** | `operation-failed` | `too-few-elements` | Identifies parent list |
| **`must` constraint** | `operation-failed` | `must-violation` | Configurable |
| **`require-instance`** | `data-missing` | `instance-required` | Path to referring leaf |
| **Mandatory `choice`** | `data-missing` | `missing-choice` | `<missing-choice>` element |
| **Invalid `insert` target** | `bad-attribute` | `missing-instance` | Path to missing key |
