# RFC 8342: Network Management Datastore Architecture (NMDA)
# Updates: RFC 7950 | Cat: Standards Track | March 2018

## 1. ABSTRACT & OBJECTIVES
* **Datastore (DS) definition**: Conceptual workspace mapping to instantiated YANG data tree.
* **Problem**: Original YANG/NETCONF model duplicated "config true" (user intent) & "config false" (runtime state) in separate branches (e.g., RFC7223, RFC7277). This led to poor readability, complex xpath filtering, and non-machine-readable relationships.
* **NMDA Solution**: Single-schema definition across multiple datastores representing config lifecycle phases:
  `[Intent] -> [Applied State] -> [Operational State]`.

---

## 2. NMDA DATASTORE LIFECYCLE ARCHITECTURE

```
    Legend: ct = config true; cf = config false; rw = read-write; ro = read-only
    +-------------+                 +-----------+
    | <candidate> |                 | <startup> | (ct, rw)
    |  (ct, rw)   |<---+       +--->| (ct, rw)  |
    +-------------+    |       |    +-----------+
           |           |       |           |
           v         +-----------+         v
           +-------->| <running> |<--------+
                     | (ct, rw)  |
                     +-----------+
                           |
                           | // Transformations (e.g., templates, inactive nodes)
                           v
                     +------------+
                     | <intended> | (ct, ro) -> Validated Intent
                     +------------+
                           |
                           | // Delays, Missing HW, Local factors
      +--------------------+------------------------+
      | (Dynamic Config)   | (System Config)        | (Learned Config)
      v                    v                        v
    +-------------------------------------------------+
    |                  <operational>                  | (ct + cf, ro)
    |             Complete Operational State          |
    +-------------------------------------------------+
```

---

## 3. CORE DATASTORE DEFINITIONS

### 3.1 Conventional Configuration Datastores (Shared Schema)
* **`<running>`**: Active configuration on device. May include unresolved elements (e.g., template code, inactive config markup). Syntactically valid.
* **`<candidate>`**: Sandbox for config manipulation before committing to `<running>`. Does not persist across reboots.
* **`<startup>`**: Config loaded at boot time. Read/Write. Persists in non-volatile memory.
* **`<intended>`**: Read-only. Represents post-transformation config (e.g., templates expanded, inactive code removed). System attempts to apply this exact state.

### 3.2 Dynamic Configuration Datastores
* **Dynamic / Ephemeral**: Configuration supplied runtime via external systems (e.g., I2RS). Volatile, bypassed by `<running>`, directly applied to `<operational>`.

### 3.3 The Operational State Datastore (`<operational>`)
* Read-only. Contains **all** active configuration ("config true") plus system state ("config false").
* **Strict Syntax**: Must adhere to schema types, structures, and hierarchies.
* **Loose Semantics**: Allows temporary semantic violations (e.g., `when`, `must`, `min-elements`, key-uniqueness) due to transitions or hardware absence.
* **Resource Behaviors**:
  * **Remnant Config**: Deleted config that remains active in `<operational>` until resources (file handles, memory) are released.
  * **Missing Resources**: Configuration for non-existent physical interfaces remains in `<intended>` but is excluded from `<operational>`.
  * **System-Controlled**: Hardware detection triggers auto-creation of system elements in `<operational>`.

---

## 4. METADATA ORIGIN ANNOTATIONS
Values in `<operational>` carry origin tags (`or:origin`) to designate source:
* `intended`: Sourced from `<intended>` datastore.
* `dynamic`: Sourced from a dynamic configuration datastore.
* `system`: Sourced from default hardware/system configurations (e.g., `lo0`).
* `learned`: Sourced from protocols (DHCP, NDP, LLDP, Routing).
* `default`: Unset nodes displaying default schema values.
* `unknown`: Origin untraceable.

## 5. IMPACTS ON YANG (RFC 7950 UPDATES)

### 5.1 XPath Context (`Section 6.1`)
When evaluating XPath in NMDA servers, the accessible tree is refined:
* **System State Context**: Accessible tree = all operational state.
* **Notification Context**: Accessible tree = Notification instance + all operational state.
* **RPC/Action Input/Output**: Accessible tree = RPC/Action instance + all operational state.

### 5.2 Actions & RPCs (`Section 6.2`)
* Actions must be executed within `<operational>` context. Target nodes must exist in `<operational>`.

## 6. CORE YANG MODULES

### 6.1 `ietf-datastores.yang`
```yang
module ietf-datastores {
  yang-version 1.1;
  namespace "urn:ietf:params:xml:ns:yang:ietf-datastores";
  prefix ds;

  revision 2018-02-14 { reference "RFC 8342"; }

  identity datastore { description "Abstract base."; }
  identity conventional { base datastore; }
  identity running { base conventional; }
  identity candidate { base conventional; }
  identity startup { base conventional; }
  identity intended { base conventional; }
  identity dynamic { base datastore; }
  identity operational { base datastore; }

  typedef datastore-ref {
    type identityref { base datastore; }
  }
}
```

### 6.2 `ietf-origin.yang`
```yang
module ietf-origin {
  yang-version 1.1;
  namespace "urn:ietf:params:xml:ns:yang:ietf-origin";
  prefix or;

  import ietf-yang-metadata { prefix md; }

  revision 2018-02-14 { reference "RFC 8342"; }

  identity origin;
  identity intended { base origin; }
  identity dynamic { base origin; }
  identity system { base origin; }
  identity learned { base origin; }
  identity default { base origin; }
  identity unknown { base origin; }

  typedef origin-ref {
    type identityref { base origin; }
  }

  md:annotation origin {
    type origin-ref;
    description "Tracks origin of config nodes inside <operational>.";
  }
}
```

## 7. ILLUSTRATIVE XML INSTANCES

### 7.1 Interface Configuration in `<intended>`
```xml
<system xmlns="urn:example:system">
  <interface>
    <name>eth0</name>
    <auto-negotiation><speed>1000</speed></auto-negotiation>
    <address>
      <ip>2001:db8::10</ip>
      <prefix-length>64</prefix-length>
    </address>
  </interface>
</system>
```

### 7.2 Corresponding Representation in `<operational>`
Shows merged runtime state (operational speed, default values, learned DHCP addresses, auto-instantiated system loopback `lo0`):
```xml
<system xmlns="urn:example:system" xmlns:or="urn:ietf:params:xml:ns:yang:ietf-origin">
  <interface or:origin="or:intended">
    <name>eth0</name>
    <auto-negotiation>
      <enabled or:origin="or:default">true</enabled>
      <speed>1000</speed>
    </auto-negotiation>
    <speed>100</speed> <!-- config false -->
    <address>
      <ip>2001:db8::10</ip>
      <prefix-length>64</prefix-length>
    </address>
    <address or:origin="or:learned">
      <ip>2001:db8::1:100</ip>
      <prefix-length>64</prefix-length>
    </address>
  </interface>
  <interface or:origin="or:system">
    <name>lo0</name>
    <address>
      <ip>::1</ip>
      <prefix-length>128</prefix-length>
    </address>
  </interface>
</system>
```
