# RFC 8040: RESTCONF Protocol

> Normalized agent-facing summary. Source: RFC 8040, Standards Track, January 2017 (updated by RFC 8527).
> Authors: A. Bierman, M. Bjorklund, K. Watsen.
> ⚠️ The previous repo map wrongly attributed this content to RFC 8341 (which is NACM). This file corrects that.
> Full text: https://www.rfc-editor.org/info/rfc8040

HTTP-based programmatic access to YANG data, compatible with (but a subset of) NETCONF datastore concepts (§1.2–§1.4). Data-model-driven: clients derive URLs and payload shapes from the YANG modules (§1.3).

## 1. Transport and security (§2) — load-bearing for yang2sdk

- RESTCONF MUST run over TLS (never plain HTTP); server presents X.509v3 (`https`, default 443).
- Client MUST validate the server certificate (path validation or pinned cert); MUST check server identity; server MUST authenticate the client (TLS certs preferred, HTTP auth allowed). Identity feeds NACM [RFC 8341].

## 2. Resources (§3)

- API root `{+restconf}` (discovered via `/.well-known/host-meta`, §3.1) with children: **`data`** (mandatory, combined config+state), **`operations`** (optional, data-model RPCs/actions), `yang-library-version` (§3.3).
- **Data resource** (§3.5): one YANG data node + descendants, addressable by request URI (list keys encoded per §3.5.3 — yang2sdk URL-quotes `ListNode(*keys)` here).
- **Operation resource** (§3.6): YANG `rpc`/`action` invoked via POST; input/output envelopes per §3.6.1–§3.6.2 (yang2sdk `Input`/`Output` models + `__call__`).
- Media types: `application/yang-data+xml` / `application/yang-data+json` (§3.2, §11.3). yang2sdk sends `application/yang-data+json`.
- Datastore resource semantics: edits behave like `:writable-running` (or auto-committed `:candidate`); server persists to startup if supported; NETCONF locks surface as `409 Conflict` / `in-use` (§1.4, §3.4).

## 3. Methods (§4) — the navigator mapping

| HTTP | RFC mode | yang2sdk navigator |
|---|---|---|
| GET/HEAD | retrieve (§4.3) | `retrieve()` |
| POST | create-resource (§4.4.1) / invoke-operation (§4.4.2) | `create()` / RPC `__call__` |
| PUT | replace (§4.5) | `replace()` |
| PATCH (plain) | merge (§4.6.1) | `update()` |
| DELETE | remove (§4.7) | `delete()` |

## 4. Query parameters (§4.8) — the `retrieve()` signature

- `content` (§4.8.1): `config` | `nonconfig` | `all` (default). yang2sdk pairs this with `model_dump(content=…)` filtering.
- `depth` (§4.8.2): `1..65535` | `unbounded` (default). Subtree depth ceiling.
- `fields` (§4.8.3): `;`-separated field selection.
- `filter` (§4.8.4), `insert`/`point` (§§4.8.5–6, user-ordered lists), event-stream `start-time`/`stop-time` (§§4.8.7–8).
- `with-defaults` (§4.8.9): `report-all` (default) | `trim` | `explicit` | `report-all-tagged`; each has a capability URI (§9.1.1), server MAY support a subset.

## 5. Errors (§7)

Error responses use the `errors` YANG-data template (`error-type/tag/severity/message/...`); HTTP status + `error-tag` drive client handling (yang2sdk re-raises `HTTPError` with status + body preserved).
